# Origamic — Vision

## One sentence

A user describes a small app; Origamic builds it in front of them, saves it to
their library, and runs it — without generating code that must be deployed.

## The thesis

Every AI app builder today generates source code (a Next.js project, a React
component tree) and hands it to the user to host. Origamic does not. An app in
Origamic is a bundle of **specs** — declarative data the runtime interprets:

| Spec | What it describes |
|---|---|
| Ontology | Object types, properties, links: what the app's data *is* |
| UI spec | A tree of catalog components bound to the ontology |
| Actions | Named, schema'd writes with validation rules |
| Bindings | Which spec references which `ObjectType@version` |
| Workspace | How saved apps are laid out together in panels |

The model's only output is specs. The runtime renders, persists and executes
them. The library is a store of specs. **The runtime is the product; the specs
are the content.**

This is the same shape that generative-UI protocols (A2UI, json-render, MCP
Apps) converged on for a single screen — a constrained catalog plus a
declarative payload — extended to the whole app: data model, writes and
layout, not just presentation.

## Why specs, not code

- Specs are **validatable before they run**: a bad spec is rejected by a
  schema; bad generated code fails in production.
- Specs are **editable in place**: the same model that built an app can revise
  it from a diff of the spec, not a diff of a codebase.
- Specs are **composable**: two apps that bind the same object type share an
  entity; two generated codebases share nothing.
- Specs are **portable**: no build, no deploy, no hosting decision.

## What is generated and what is not

| Generated by the model | Never generated |
|---|---|
| Ontology changes (as versioned migrations) | Data connections |
| UI specs over the catalog | Catalog components |
| Action definitions | Storage adapters |
| Small pure transforms (later, sandboxed, type-checked) | Auth, tenancy, permissions |
| Workspace layouts | The runtime |

The valuable engineering is the contract surface — the ontology primitives,
the component catalog, the action protocol. The model composes over that
surface.

## Who it is for, in order

1. **Builders** — one person making tools for themselves. This is v1.
2. **Builder-consumers** — people whose own recurring work the apps serve, so
   the library gets *reused*, not admired and abandoned. This is the first
   real test: are saved apps still in use a month later?
3. **Consumers** — people who use apps and never see the builder. The
   ambition; not v1.

Three properties cannot be retrofitted and are non-negotiable from the first
commit, because the consumer stage depends on them:

1. UI binds to the ontology only. No spec references storage.
2. Every write is a named action.
3. Every spec is versioned, and bindings reference versions.

## Non-goals for v1

- Dataflow / pipes between apps. Actions plus derived views first; explicit
  pipes when a real workflow demands one.
- Model-generated functions. Pure declarative until it demonstrably isn't
  enough.
- Multi-tenancy, sharing, governance.
- Generating anything the user must host.

## Prior art to mine, not compete with

Palantir Foundry Ontology (object/link/action — ignore the rest), Retool and
Appsmith (datasource/query abstraction), Airtable Interfaces, Observable
(reactivity model), Anthropic artifacts-with-storage (a tiny version of this
minus the ontology), FDC3 (intents and context channels between panels).
